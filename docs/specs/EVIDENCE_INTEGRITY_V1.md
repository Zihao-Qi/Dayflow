# Evidence Integrity v1

Status: Implemented
Date: July 27, 2026
Scope: Evidence Integrity corrective release

## Purpose

Dayflow promises an honest account of what was planned, what happened, and what
moved forward. This specification makes that promise enforceable by defining one
canonical evidence model across Focus, Activity, Projects, Journal, and Review.

It supersedes any implementation behavior that derives competing time totals
from Focus Sessions and Activities or treats missing evidence as neutral
evidence. Existing product specifications remain in force where they do not
conflict with this document.

## Goals

- Make Activity the canonical record of time spent.
- Make Focus completion create evidence exactly once.
- Keep Task completion independent from time evidence.
- Distinguish review-period metrics from all-time metrics.
- Preserve direct and Task-inherited Project attribution without conflicts.
- Represent missing evidence honestly.
- Make retry, reload, and multi-tab behavior deterministic.

## Non-Goals

- Automatically completing Tasks when a timer finishes.
- Inferring productivity, quality, or Project completion from time spent.
- Replacing manual Activity capture.
- Adding billing-grade time tracking.
- Designing new charts or visual treatments.
- Adding hosted collaboration or cross-user synchronization.

## Canonical Terms

### Activity

An Activity is the canonical persisted record that time was spent. Every
duration shown as spent, focused, or invested is derived from Activities unless
a screen is explicitly labeled as timer telemetry.

Activities may be created manually or generated by a completed Focus Session.
Their origin must be distinguishable.

### Focus Session

A Focus Session is the lifecycle record for a timer: its intended duration,
timestamps, pause state, completion state, and optional Task or Project context.
It is not a second source of invested time.

### Focus Activity

A Focus Activity is the one Activity generated from a completed Focus Session
with at least one full elapsed minute. It retains a unique reference to its
source Focus Session.

### Invested Time

Invested Time is the all-time sum of Activities attributed to a Project,
directly or through one of its Tasks.

### Review-Period Invested Time

Review-Period Invested Time is the sum of attributed Activities whose
`startedAt` falls within the active Review Period. It must never be labeled
simply as Invested Time when displayed beside an all-time value.

### Review Period

The default Review Period is the seven local calendar days ending today:
`startOfLocalDay(today - 6 days)` inclusive through
`startOfLocalDay(tomorrow)` exclusive.

### Missing Evidence

Missing Evidence means no record was created. It is distinct from a recorded
zero, a neutral mood, or a neutral energy value.

## Invariants

1. **One canonical duration ledger.** Activity durations are the source of truth
   for daily spent time, weekly actual time, Project Invested Time, and
   Review-Period Invested Time.
2. **Exactly one Focus Activity.** A completed Focus Session with at least one
   full elapsed minute has exactly one generated Activity. Zero-minute,
   canceled, and Break Sessions have none.
3. **Atomic completion.** Marking an eligible Focus Session completed and
   creating its Focus Activity succeed or fail together.
4. **Idempotent completion.** Repeating or racing the same completion request
   returns the persisted result and never creates another Activity.
5. **One active timer.** At most one Focus or Break Session may be Running or
   Paused across all tabs.
6. **Independent Task status.** A Focus Session never completes its Task by
   inference. A user may explicitly complete the Task during the completion
   handoff as a separate, auditable choice.
7. **No double counting.** A generated Focus Activity contributes to Activity
   totals once. Its source Focus Session does not contribute a second duration.
8. **Consistent Project attribution.** Evidence linked to a Project Task derives
   Project attribution from that Task. Direct `projectId` is used only when no
   Project Task supplies attribution.
9. **No conflicting attribution.** An Activity, Note, or Material cannot name a
   direct Project that differs from the linked Task's Project.
10. **Reads do not manufacture evidence.** Loading Today, Journal, Review, or a
    bootstrap endpoint cannot create Diary entries, Activities, or other
    evidence.
11. **Absence remains absent.** A day without a Diary entry reports mood and
    energy as missing, not as default values.
12. **Period labels match period filters.** Any metric labeled “today,” “this
    week,” or “review period” is filtered to that exact local-day interval.

## Focus Completion Workflow

### Automatic or Manual Completion

When an active Focus Session reaches its planned duration or the user finishes
it early:

1. Compute elapsed whole minutes from persisted timestamps and accumulated
   pauses, capped at the planned duration.
2. In one transaction:
   - move the Focus Session to Completed;
   - persist the computed actual minutes;
   - when actual minutes are at least one, create or retrieve the single Focus
     Activity linked to that session.
3. Return the completed session and generated Activity identifiers.
4. Show the completion handoff for optional enrichment.

The generated Activity initially uses the Focus Session label or linked Task
title and the default focus category. The time is already canonical at this
point.

### Completion Enrichment

The completion handoff may update:

- Activity note;
- Activity category;
- explicit Task completion;
- the user's next Focus or Break choice.

Closing or deferring the handoff does not remove the Activity or prevent another
session from starting. Enrichment updates the existing Activity; it never
creates a replacement.

### Starting the Next Queue Item

Starting the next item is separate from committing the completed session. If
the next start fails:

- the completed Focus Session and its Activity remain committed;
- the UI refreshes to the persisted completed state;
- the next item remains available to retry;
- the completed session is not presented as unrecorded.

## Attribution Rules

### Task-Linked Evidence

When a linked Task belongs to a Project:

- its Project supplies the effective attribution;
- a separate direct Project selection is hidden, synchronized, or rejected;
- changing the Task's Project affects future evidence only. Existing Activity
  attribution remains historically stable unless the user explicitly edits it.

### Direct Project Evidence

When no linked Task supplies a Project, the user may optionally select one
Project directly for an Activity, Note, Material, or Focus Session.

### Standalone Evidence

Evidence may belong to neither a Task nor a Project. Standalone evidence remains
valid and contributes to daily and review totals but not Project totals.

## Aggregation Rules

### Daily and Review Actual Time

For each local day:

```text
actual minutes = sum(Activity.durationMinutes where Activity.startedAt is in day)
```

Manual Activities and Focus Activities are additive. Legacy Task actual minutes
may be used only as a temporary compatibility fallback on days with no
Activities, and the fallback must be removed after migration.

### Focused Time

Focused time is the sum of Activities whose origin is Focus. If the data model
cannot distinguish origins, Dayflow must add that distinction before presenting
an Activity-derived focused total.

### Project Metrics

```text
all-time invested =
  all attributed Activity durations

review-period invested =
  attributed Activity durations whose startedAt is in Review Period
```

Project detail may show both values if they are clearly labeled. A weekly budget
must be compared only with Review-Period Invested Time, never the all-time
value.

### Project Movement

A Project “moved forward” during a Review Period when at least one of these
occurred inside the period:

- a Project Task was completed; or
- an attributed Activity was recorded.

Notes and Materials may support the evidence narrative but do not independently
mark movement.

## Diary Evidence

- GET and bootstrap requests return an absent Diary entry as `null` or an
  explicit empty draft that is not persisted.
- A Diary entry is created only by an intentional save.
- Mood and energy become evidence only after that save.
- An intentionally saved value of 3 is different from no value.
- Empty content may still be saved when mood, energy, or reflection was
  intentionally recorded.

## API and Storage Requirements

- Add a nullable unique Focus Session reference to Activity, or an equivalent
  database-enforced uniqueness relationship.
- Enforce the one-active-session rule at the transactional persistence boundary,
  not only with a preflight query.
- Completion and enrichment endpoints are safe to retry.
- Mutation responses return the canonical persisted entity or an explicit
  domain error.
- Project/Task relationship validation occurs before persistence.
- Invalid enum, date, duration, and relationship inputs produce a typed 4xx
  response, never an unhandled database error.

## Existing-Data Reconciliation

Before enabling the new calculations:

1. Identify completed Focus Sessions with no corresponding Activity.
2. Match safely identifiable Activities to their Focus Sessions.
3. Create missing Focus Activities where elapsed minutes are at least one.
4. Flag ambiguous possible duplicates for a deterministic migration rule; do
   not silently add both.
5. Populate the Activity origin and Focus Session relationship.
6. Recompute Review and Project metrics from Activities.
7. Preserve existing manual Activities unchanged.

The reconciliation must be repeatable without creating additional records.

## Acceptance Criteria

1. Completing a 25-minute Focus Session creates one 25-minute Activity in the
   same successful operation.
2. Two simultaneous completion requests still produce one Activity.
3. Reloading during or after completion does not lose or duplicate evidence.
4. A day with 25 focus minutes and 60 manual Activity minutes reports 85 actual
   minutes and 25 focused minutes.
5. A Project with ten all-time hours and two hours in the Review Period displays
   those as distinct values and compares its weekly budget with two hours.
6. Finishing a Focus Session leaves the linked Task unfinished unless the user
   explicitly completes it.
7. A failed attempt to start the next queue item does not make the completed
   session appear unrecorded.
8. Two tabs cannot create two active sessions.
9. A Task-linked Activity cannot be assigned to a conflicting direct Project.
10. Opening Review on a day without a Diary entry does not create one and shows
    mood and energy as missing.
11. Canceled, Break, and zero-minute Focus Sessions do not add invested time.
12. All period-boundary tests use the user's local calendar day, including
    daylight-saving transitions.

## Required Test Coverage

- Unit tests for elapsed-time and period calculations.
- Storage tests for uniqueness, atomic completion, and attribution constraints.
- API contract tests for validation, retries, and typed failures.
- Multi-request tests for completion and active-session races.
- Browser tests for completion enrichment, failed next-session start, missing
  Diary evidence, and correct Review labels.

## Release Gate

This specification is complete when:

- all invariants are enforced by code and tests;
- existing Focus evidence is reconciled;
- Review and Project displays use the canonical calculations;
- the Focus Timer and Projects specifications link to this document for evidence
  rules;
- no known screen derives spent or invested time directly from Focus Sessions.
